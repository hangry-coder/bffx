# Integration notes: Supabase

**Verdict:** Postgres as primary `Store` — **Stable** when you use a normal Postgres URL. Supabase Auth, Storage, and Realtime are **not** first-class BFFX surfaces.

## What works today

- Point `spec.store` at Supabase’s Postgres connection string (pooler or direct). Same rules as any Postgres deployment: run migrations, set `DATABASE_URL` / `BFFX_STORE_MODE=postgres` per [`docs/guides/operations.md`](../../guides/operations.md).

## What you bridge yourself

- **Auth:** Keep BFFX JWT + policies on the server; optionally sync users from Supabase Auth into a `User` resource via hooks if you need a single user row.
- **Storage / Realtime:** Use Supabase client SDKs from mobile, or call Supabase HTTP APIs from Go hooks — not generated by manifests.

## Gotchas

- Row Level Security (RLS) in Supabase does not replace BFFX policies unless every query goes through Supabase’s client with user context; mixing BFFX CRUD with Supabase RLS is easy to get wrong.
- Prefer one source of truth for authorization: either BFFX policies on your API or explicit service-role access from hooks only.

## Native driver?

- No separate “Supabase driver” — Postgres is the integration. Open an issue if you want a documented `supabase://` URL helper or connection pool presets.
